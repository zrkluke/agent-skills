# 研究與規劃：階段 1～5

提問、設計與規劃者先讀專案工作規則及需求；第 2 階段的獨立研究者只接收研究問題與必要入口，不讀需求全文或其他設計產物。以下檔名僅為建議。

## 1. 提問：產生研究題目

需求可在這個階段出現。將它轉為查現況的問題，例如入口、呼叫鏈、資料與狀態、失敗處理、相似寫法、現有測試。每題附必要的範圍或來源入口。

問題應是「付款失敗後目前在哪裡還原狀態？」，而非「應該新增哪個補償服務？」。不要把建議解法或需求全文包進研究題目。這一步的主要產物是 `questions.md`，不代表要先問使用者一長串問題。

## 2. 研究：隔離需求，查明事實

可用且已允許委派時，交給不繼承父對話的研究者；在支援此參數的環境可用 `fork_turns="none"`。只傳研究問題、必要的專案工作規則、程式位置與本階段的查核要求，不傳需求全文、預定設計、其他階段產物或父對話。不要指示研究者先讀完整任務紀錄，也不要只叫已知需求的研究者「忽略需求」就當作隔離完成。

這是輸入上下文的分隔，不代表研究者已受到檔案存取隔離。工具無法建立新上下文時，明示「未實現需求隔離」，仍可做唯讀事實調查，不假裝已達成相同隔離效果。

寫入 `research.md`：

- 逐題回答目前的執行路徑、資料與介面契約、既有模式、限制與測試位置。
- 附檔案／符號／必要行號及核對版本，讓別人能回查。
- 區分程式直接證據、實際執行觀察、推論及未查清處。
- 不提改法、不評選未來架構；查不到就列未知，不補成事實。

## 3. 設計：對齊目標與取捨

主代理重新合併需求與研究結果，產出精簡的 `design.md`：現況、目標與不做的範圍、沿用模式、重要選項及取捨、已確認決定、待決問題、成功條件。

文件要短到人能有效審閱；文章的約 200 行是量級參考，不是配額。優先攤開可能誤解的地方，不靠大量實作細節掩蓋重要選擇。

將具體設計與重要取捨交給使用者修正方向，取得共識後才固定後續拆分。既有決定直接引用，已授權自行判斷的取捨照授權處理；未回覆不算同意。

## 4. 結構大綱：先拆出可驗證增量

設計的必要決定就緒後寫 `outline.md`。說明各增量的結果、順序與相依關係，列出關鍵介面／型別輪廓、涉及區域，以及每階段的自動或人工檢查。

判斷切分是否合適：每個增量完成後，都能用某個實際操作、查詢或測試辨識其結果，而不是只得到一整層尚無法接起來的程式。

例如先接起一條使用固定資料的查詢路徑，再沿相同路徑接入真實儲存與錯誤處理。固定資料只證明當時的路徑可用，不能當作持久化或完整整合已驗證。沿用專案既有切分與驗證要求。

大綱給人看全貌，保持短而可討論。尚未確認時，先交大綱供回饋，不直接展開長計畫或實作；已有確認或代決策授權時直接接續。要求修訂大綱本身不代表實作授權。

## 5. 計畫：把大綱轉成實作步驟

依已確認大綱展開 `plan.md`，每個增量寫明：

- 具體修改位置與既有模式；必要的新介面或資料契約。
- 驗收條件、必要回歸、自動／人工檢查與可辨識的預期結果。
- 實際存在的相依前置與重要風險。

先核對引用位置存在，不靠猜測產生大量程式或完整檔案替換稿。詳細計畫是實作者的工作清單；保留設計與大綱作為人的主要對齊入口，不要求使用者逐行讀長計畫才能進行任何工作。

只做規劃的任務在此交付。已有完整實作授權且沒有待決阻擋時，使用相同產物接續第 6 階段；否則清楚列出已就緒部分與待決事項。
