# 從研究到實作

把現況事實、設計決策、實作順序與程式變更分開，讓錯誤假設在大量寫程式前被看見。本技能依 Dex Horthy 的 CRISPY 演講整理文章所述八階段改寫，屬跨專案流程，並非 Dex 官方技能。

## 選擇執行範圍

- **研究規劃**：執行 1～5，不修改產品程式。使用者只要求研究或設計時，完成指定階段即可。
- **接續實作**：讀取既有產物，從第一個未完成階段繼續；已確認事項不重問，不重新產生整套文件。
- **完整開發**：在已有實作授權下接續 6～8；仍依專案規則及既有授權處理提交、推送與 PR。

| 階段 | 核心問題 | 交付內容 |
| --- | --- | --- |
| 1 提問 Questions | 為了理解現況，需要查清什麼？ | 可供研究者回答的現況問題 |
| 2 研究 Research | 系統現在實際如何運作？ | 有來源定位的客觀事實與未知處 |
| 3 設計 Design | 要變成什麼樣，為什麼這樣選？ | 目標、取捨、已確認決定與待決問題 |
| 4 結構大綱 Structure Outline | 分幾個可驗證增量，順序如何？ | 垂直切分的階段、介面輪廓與檢查點 |
| 5 計畫 Plan | 每個增量具體改哪裡、怎麼驗？ | 給實作者使用的詳細步驟 |
| 6 工作區 Worktree | 在哪個隔離工作區執行？ | 已核對的路徑、分支、基線及準備結果 |
| 7 實作 Implement | 每個增量是否真的可運作？ | 程式、必要測試、執行證據與進度 |
| 8 PR Pull Request | 差異是否符合設計，如何審查？ | 可審查的完整差異與 PR，或授權範圍內的草稿 |

## 按階段載入

- 執行 1～5 才讀 [研究與規劃](references/planning.md)。
- 執行 6～8 才讀 [實作與交付](references/implementation.md)。
- 要核對演講轉述、現行官方流程與本技能改寫的差別時，讀 [來源與改寫界線](references/source-notes.md)。

## 核心原則

1. 研究先回答「現在如何」，不要混入「應該改成什麼」。需求轉成問題後，研究者以新的上下文接手，避免先入為主。
2. 人的主要檢查重點是短設計文件、短大綱與實際程式差異；詳細計畫服務實作，不能取代讀程式碼。
3. 設計與大綱是方向校正點。尚未取得共識時，先呈現具體內容供使用者回饋，再展開後續詳細計畫；不可自行把草稿認定為已確認。既有確認或明確授權代決策時直接沿用，不重複卡關。
4. 每個增量都要能執行、觀察或查詢，避免把所有資料層做完才做所有介面。沒有前後端的專案同樣按可驗證行為切分。
5. 重要決定與更正寫回對應文件。以專案規範和使用者最新明確決定為準，AI 草稿不能自行推翻已確認需求；查實際現況以目前程式與執行證據為準。

## 跨階段交接

沿用專案既有文件位置與命名；以下參考檔名不是額外必建的文件清單。換上下文前，在現有大綱或計畫記錄目前版本、已確認決定、完成情況、未決問題與下一步，不另建一份進度表。接手時讀取必要產物並核對程式版本。

技能約定流程，不等於自動編排程式；研究輸入分隔與階段切換必須由實際工具執行，不能只靠提示就宣稱已強制保證。
